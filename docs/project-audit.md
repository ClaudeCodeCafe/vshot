# vshot プロジェクト監査レポート

- **調査日**: 2026-07-10
- **対象**: v0.3.0(コミット `8904ca6`、main ブランチ)
- **手法**: 全ファイル読解、shellcheck 0.11.0、および実機での挙動検証(macOS / ffmpeg / ImageMagick)。各項目に「実測確認済み」「未検証」を明記。

## 総評

9 ラウンドの Codex レビューを経ており、bash スクリプトとしての堅牢性は高い水準にある(`--` によるパス保護、`awk -v` による注入対策、フォント 3 段フォールバック、実行単位の RUN_ID プレフィックス等)。秘匿情報のハードコードや外部送信は存在しない。

一方で、**コアの価値提案(モンタージュ 1 枚を AI が読む)に対して、モンタージュの実寸が Claude の画像縮小制限を大きく超えるケースがある**点が最大の課題。また「macOS bash 3 互換」を宣言しながら CI に macOS ランナーがない点、プラグイン内ドキュメント(SKILL.md / watch.md / CLAUDE.md)間の乖離が目立つ。

## 1. Enhancement(既存機能の改善)

### E1. モンタージュ解像度が Claude vision の縮小制限を超え、text mode の目的が損なわれる

- **カテゴリ**: Enhancement
- **対象**: `vshot:654-706`(モンタージュ生成)、`skills/video-analysis/SKILL.md`(text mode + 16 frames を推奨)
- **現状の問題点**: 実測確認済み — `--mode text --frames 16 --montage` は横動画で **4840×2192**、縦動画で 1550×2192 のモンタージュを生成する。Claude API は長辺 1568px 超の画像を縮小するため、960px 幅のセルが実効 ~310px まで潰れ、「テキストが読める」という text mode の目的が崩れる。README のトークン試算(~1,500 tokens)は縮小後の値であり、縮小自体は暗黙の前提になっているが、**縮小によるセル解像度の損失がどこにも考慮・警告されていない**。
- **提案内容**: (1) モンタージュ長辺が 1568px を超える場合に「セル実効解像度が落ちる」旨の警告と推奨フレーム数を stderr に表示。(2) 長辺が閾値内に収まるよう複数枚に自動分割する `--pages` オプション(`--json` の `montage` を配列化)。まず (1) だけでも価値がある。
- **優先度**: **High** — ツールの中核ユースケース(CCC Phase B QC での text mode 運用)に直接影響し、ユーザーは劣化に気づけない。
- **想定工数**: S(警告のみ)/ M(自動ページ分割まで)

### E2. `--scene` に不正な閾値を渡すと「multiple video files not supported」と誤誘導される

- **カテゴリ**: Enhancement
- **対象**: `vshot:201-207`(--scene のオプション解析)
- **現状の問題点**: 実測確認済み — `vshot video.mp4 --scene 1.5` は閾値の正規表現(0.0〜1.0)にマッチしないため `1.5` が 2 本目の動画パスとして解釈され、`Error: multiple video files not supported` という無関係なエラーになる。`--scene -0.1` も `Unknown option: -0.1`。ユーザーは自分のミスの内容を特定できない。
- **提案内容**: 数値らしき引数(`^[0-9.+-]`で始まる等)が続くのに範囲外の場合は「Error: --scene threshold must be 0.0-1.0, got '1.5'」と明示的にエラーにする。
- **優先度**: **High** — 現場ユーザーが閾値調整を試行錯誤する機能(README も 0.5 等の調整を案内)であり、遭遇確率が高い。修正は数行。
- **想定工数**: S

### E3. `--cleanup` / `--cols` が `--montage` なしだと黙って無視される

- **カテゴリ**: Enhancement
- **対象**: `vshot:655`(cleanup は montage ブロック内のみ)、`vshot:659`(cols も同様)
- **現状の問題点**: 実測確認済み — `vshot video.mp4 --cleanup --frames 2` はフレームを削除せず、警告も出ない。「cleanup = 出力を掃除」と期待したユーザーは全フレームが残ることに気づかない。
- **提案内容**: `--montage` なしで `--cleanup` / `--cols` が指定された場合に「--cleanup has no effect without --montage」と警告する(もしくは help に明記)。
- **優先度**: Medium — 実害はディスク残骸程度だが、無言の無視は信頼を損ねる。
- **想定工数**: S

### E4. 均等サンプリングが動画全編をデコードするため長尺動画で遅い

- **カテゴリ**: Enhancement
- **対象**: `vshot:406-414`(fps フィルタによる抽出)
- **現状の問題点**: デフォルトの `--frames N` は `fps=N/duration` フィルタで実装されており、ffmpeg が**全フレームをデコード**する。20 フレーム欲しいだけでも 1 時間の 4K 動画を全編デコードすることになる。一方 `--at` モードは `-ss` シークで実装済み(`vshot:463-484`)。
- **提案内容**: `--frames` モードでも各時刻を計算して `--at` と同じシークベース抽出に統一する。タイムスタンプが正確になる副次効果もある(現在は抽出後に `i * STEP` で近似)。長尺でのシーク優位は一般知識ベースで、閾値(何秒以上でシークが勝つか)は未検証 — ベンチマークを取ってから切り替え判断を推奨。
- **優先度**: Medium — 現場の主対象(数十秒〜数分の CCC 動画)では現状でも許容範囲。長尺対応時に効く。
- **想定工数**: M

### E5. タイムスタンプ焼き込みがフレーム毎の再エンコードで、遅くかつ画質が二重劣化する

- **カテゴリ**: Enhancement
- **対象**: `vshot:586-652`(burn-in ループ)
- **現状の問題点**: フレームごとに ffmpeg(または ImageMagick)を 1 プロセスずつ起動し、JPEG を**デコード→焼き込み→再エンコード**している。N フレームで N プロセス + JPEG 二重圧縮による画質劣化が発生する。
- **提案内容**: 抽出パスの `-vf` に `drawtext=text='%{pts\:hms}'` を組み込み、抽出と焼き込みを 1 パス化する(未検証 — scene/fps フィルタとの併用時の PTS 表示は要動作確認)。成立すればプロセス数は 1 になり二重圧縮も消える。フォールバック(ImageMagick / ファイル名埋め込み)の既存構造はそのまま残せる。
- **優先度**: Medium — 動作は正しいが、20〜30 フレームで体感差が出る。
- **想定工数**: M

### E6. 1 時間超の動画でタイムスタンプが「75:00」のような分表示になる

- **カテゴリ**: Enhancement
- **対象**: `vshot:110-112`(`format_ts`)、`vshot:577-578`(ファイル名サフィックス)
- **現状の問題点**: 実測確認済み — `format_ts 4500` は `75:00` を返す。H:MM:SS 形式がなく、1 時間超では読み手(AI 含む)が誤解しうる。
- **提案内容**: 3600 秒以上のとき `1:15:00` 形式に切り替える。ファイル名サフィックス(`t75m00s`)も同様。
- **優先度**: Low — 現場の主対象は短尺動画。
- **想定工数**: S

### E7. scene 0 件時(exit 2)の状態が `--json` 出力から判別できない

- **カテゴリ**: Enhancement
- **対象**: `vshot:120-142`(`emit_json`)、`vshot:503-527`(exit 2 パス)
- **現状の問題点**: `--scene` で 0 フレームのとき exit 2 で JSON も出るが、JSON 自体には `frames: 0` 以外の手掛かりがない。パイプライン側は exit code を別途拾う必要があり、`vshot ... | jq` のようにパイプすると exit code が失われる。
- **提案内容**: JSON に `"status": "ok" | "no_scenes"`(または `"exit_code"`)フィールドを追加する。README に exit code 一覧(0/1/2)も記載する(D3 と連動)。
- **優先度**: Low
- **想定工数**: S

### E8. リリースフローに Homebrew tap の formula 更新が含まれていない

- **カテゴリ**: Enhancement
- **対象**: `.github/workflows/release.yml`、`README.md:49-56`(Homebrew を推奨インストールとして案内)
- **現状の問題点**: README は Homebrew を「Recommended」としているが、release ワークフローは GitHub Release 作成までで、`ClaudeCodeCafe/tap` の formula 更新は自動化されていない(tap 側の自動化有無は本リポジトリからは未検証)。リリースの度に手動更新が必要なら、brew ユーザーには古い版が配られ続ける。
- **提案内容**: release.yml に tap リポジトリへの formula bump(`repository_dispatch` か PAT での直接コミット)を追加。tap 側に自動化が既にあるなら、その旨を CLAUDE.md に記録してこの項目をクローズ。
- **優先度**: Medium — 配布チャネルの鮮度に直結。
- **想定工数**: M

## 2. Refactoring(内部品質)

### R1. トップレベルに約 500 行の手続きコードが直書きされている

- **カテゴリ**: Refactoring
- **対象**: `vshot:175-775`(引数解析以降のメインフロー)
- **現状の問題点**: 関数化されているのは補助処理のみで、probe → 抽出 → リネーム → 焼き込み → モンタージュ → サマリの主要フローが全てトップレベルにあり、グローバル変数(`FRAME_FILES`, `TS_FAILURES`, `EXTRACTED` 等)を暗黙に共有している。変更時の影響範囲が読みにくい。
- **提案内容**: 「単一ファイル」方針(CLAUDE.md)は維持したまま、`probe_video` / `extract_frames` / `assign_timestamps` / `burn_timestamps` / `create_montage` に関数分割し、末尾に `main "$@"` を置く構成にする。共有状態はグローバルのままでよい(bash 3 制約下では妥当)が、各関数の入出力をコメント 1 行で明示する。
- **優先度**: Medium — 機能追加(E1 のページ分割等)の前にやると後続が楽になる。
- **想定工数**: M

### R2. モンタージュのフォント再検出リトライが実質デッドコード

- **カテゴリ**: Refactoring
- **対象**: `vshot:712-720`
- **現状の問題点**: 1 回目の `run_montage` 失敗後、`DETECTED_FONT` が空なら `detect_font` を再実行してリトライするが、`detect_font` は直前(`vshot:678`)に呼ばれて空だったばかりで、同一環境で再実行しても結果は変わらない。到達しても常に同じ失敗を繰り返すだけのパスになっている(コード読解による判断、実行トレースは未検証)。
- **提案内容**: このリトライブロックを削除し、失敗時は既存のラベルなしフォールバック(`vshot:721-728`)へ直行させる。
- **優先度**: Medium — 動作害はないが「フォールバックが 4 段あるように見えて実は 3 段」という誤解を将来の変更者に与える。
- **想定工数**: S

### R3. モンタージュパスの計算が 2 箇所に重複している

- **カテゴリ**: Refactoring
- **対象**: `vshot:675`(`MONTAGE_FILE=`)と `vshot:769`(`MONTAGE_PATH=` の再構築)
- **現状の問題点**: `${OUTPUT_DIR}/${BASENAME}_montage_${RUN_ID}.jpg` という命名規則が 2 箇所に書かれており、片方だけ変更すると「Feed to AI」表示と実ファイルが乖離する。
- **提案内容**: サマリ表示では `MONTAGE_FILE` を絶対パス化して再利用する。
- **優先度**: Low
- **想定工数**: S

### R4. scene 0 件時のメッセージブロックが 2 箇所に重複

- **カテゴリ**: Refactoring
- **対象**: `vshot:520-527` と `vshot:540-547`
- **現状の問題点**: 「No scene changes detected…」の警告 + サイズ表示 + `emit_json` + `exit 2` がほぼ同一内容で 2 回書かれている(ffmpeg が非 0 で終わった場合と 0 で終わった場合)。
- **提案内容**: `report_zero_scenes()` 関数に括り出す。
- **優先度**: Low
- **想定工数**: S

### R5. ffprobe を 4 回呼んでいる(duration / width / height / rotation)

- **カテゴリ**: Refactoring
- **対象**: `vshot:297`, `332`, `337`, `356`
- **現状の問題点**: 1 回の `ffprobe -show_entries stream=width,height:stream_side_data=rotation:format=duration` で取得できる情報を 4 プロセスに分けており、コードも 4 ブロックに膨らんでいる。
- **提案内容**: 1 回の呼び出しにまとめてパースする(bash 3 互換の範囲で `while read` 分解)。起動コスト削減は微小だが、エラーハンドリングが 1 箇所に集約される効果が大きい。
- **優先度**: Low
- **想定工数**: S

### R6. フレーム数カウント(find)とリネーム対象(glob)の走査基準が不一致

- **カテゴリ**: Refactoring
- **対象**: `vshot:501`(`find "$OUTPUT_DIR" -name ...` — `-maxdepth 1` なし)と `vshot:565`(トップレベルのみの glob)
- **現状の問題点**: `EXTRACTED` は再帰的に数えるが、リネームループはトップレベルの glob のみを走査する。RUN_ID プレフィックスのおかげで実害はほぼないが(未検証)、`tests/smoke.sh` は `-maxdepth 1` を付けており基準が揃っていない。
- **提案内容**: `find` に `-maxdepth 1` を追加して基準を統一する。
- **優先度**: Low
- **想定工数**: S

## 3. Feature(新機能候補)

### F1. `--range START-END` — 時間範囲を指定した抽出

- **カテゴリ**: Feature
- **対象**: `vshot`(引数解析・抽出ロジック)
- **現状の問題点**: `--at` でピンポイント再抽出はできるが、「3:00〜4:30 だけ細かく見たい」という範囲指定ができない。watch.md のステップ 7(怪しい箇所の再検査)では複数時刻を手で列挙する必要がある。
- **提案内容**: `--range 180-270` で該当区間のみを対象に `--frames` / `--interval` / `--scene` を適用する。ffmpeg の `-ss`/`-to` を入力側に付けるだけで既存フィルタと組み合わせられる見込み(未検証)。
- **優先度**: Medium — 既存の「概観 → 深掘り」ワークフローの自然な補完。
- **想定工数**: M

### F2. `--audio` — 音声トラックの抽出(文字起こし連携)

- **カテゴリ**: Feature
- **対象**: `vshot`(新フラグ)、`commands/watch.md`
- **現状の問題点**: 「AI が動画を観る」は実現したが音声は完全に捨てている。ナレーションや BGM の有無は QC 観点で重要になりうる。
- **提案内容**: `--audio` で `audio.m4a`(または 16kHz mono wav)を出力ディレクトリに書き出し、`--json` に `"audio"` フィールドを追加。文字起こし自体は外部(whisper 等)に委ね、依存を増やさない方針を維持する。
- **優先度**: Low — 現場ニーズの確認が先。
- **想定工数**: M

### F3. 複数動画のバッチ処理

- **カテゴリ**: Feature
- **対象**: `vshot:222-228`(現在は明示的にエラー)
- **現状の問題点**: `Error: multiple video files not supported` と実装側で意識されており、構想の痕跡がある。QC で複数テイクを比較する場合は 1 本ずつ実行が必要。
- **提案内容**: 複数パスを受け取り動画ごとに出力ディレクトリを分けて順次処理、`--json` は 1 動画 1 行(JSON Lines)。
- **優先度**: Low — シェルの for ループで代替可能。
- **想定工数**: M

### F4. `--format webp` — 出力フォーマット選択

- **カテゴリ**: Feature
- **対象**: `vshot`(抽出・モンタージュの拡張子/エンコーダ)
- **現状の問題点**: JPEG 固定。WebP なら同等画質でファイルサイズを 25〜30% 程度削減できる見込み(一般知識ベース、未検証)。Claude の Read は WebP を読める。
- **提案内容**: `--format jpg|webp|png` を追加。ffmpeg/ImageMagick 両方の WebP サポート有無をチェックしてフォールバックする。
- **優先度**: Low — トークン数は画素数で決まるためサイズ削減の実益はディスクと転送のみ。
- **想定工数**: S

### D2. SKILL.md が旧方式(ls -t)のままで watch.md と手順が不一致

## 5. セキュリティ(追加チェック結果)

### S1. 総合評価: 良好(重大な問題なし)

- **確認済み(コード読解 + 一部実測)**:
  - 秘匿情報のハードコード: なし。外部へのデータ送信: なし。
  - コマンド注入対策: ユーザー入力は正規表現で検証後に使用(`--scene` → ffmpeg フィルタ、`--at` → `awk -v`)。パス操作は `--` 区切りで保護。特殊文字入りファイル名(スペース・`$`・引用符)での実行は実測で正常動作を確認済み。
  - 依存パッケージ: ffmpeg / ImageMagick はシステム管理でリポジトリに依存ロックなし(既知脆弱性はユーザー環境依存 — 本リポジトリの管轄外)。

### S2. json_escape が制御文字をエスケープしない

- **カテゴリ**: Enhancement(堅牢性)
- **対象**: `vshot:115-117`
- **現状の問題点**: `\` と `"` のみエスケープしており、改行やタブ等の制御文字を含むファイル名では不正な JSON が出力される(理論上の指摘、未検証 — 通常のファイル名では実測で valid JSON を確認済み)。
- **提案内容**: 改行・タブは現実に発生しうるため `sed` に `\n` `\t` の変換を追加するか、awk で 0x00-0x1F を `\uXXXX` に落とす。
- **優先度**: Low — 攻撃面ではなく堅牢性の問題(出力を読むのは自分のパイプライン)。
- **想定工数**: S

### S3. GitHub Actions がタグピン(@v4)で SHA ピンされていない

- **カテゴリ**: Enhancement(サプライチェーン)
- **対象**: `.github/workflows/ci.yml`, `release.yml`
- **現状の問題点**: `actions/checkout@v4` はタグ参照であり、タグの差し替えに対して脆弱。release.yml は `contents: write` を持つため影響が出る場所ではある。
- **提案内容**: SHA ピン + Dependabot(`package-ecosystem: github-actions`)で追従する。
- **優先度**: Low — 使用アクションは公式 1 つのみでリスクは小さい。
- **想定工数**: S
